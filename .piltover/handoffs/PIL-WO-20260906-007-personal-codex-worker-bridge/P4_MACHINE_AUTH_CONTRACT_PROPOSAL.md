# P4 Machine Authentication and Transport Contract Proposal

## Status

APPROVED

Owner approval was granted on 2026-09-06 by the P4 Gate Resolution R1 execution authorization. The approved contract is the opaque bearer credential and HTTPS polling route defined below; the alternative options remain historical decision evidence only.

## Problem

The canonical package requires authenticated, revocable Worker identity and an outbound resumable connection, but does not define enrollment, credential form, server-side verification storage, rotation, expiration, replay behavior, recovery, or a concrete transport. These choices alter the machine trust boundary, public protocol, persistence, and operations. They cannot be inferred from Worker registration, capabilities, tenant grants, or leases.

Piltover Worker authentication and Codex/OpenAI authentication remain separate security domains. No ChatGPT token, OpenAI API key, Codex credential, `auth.json`, or browser cookie may authenticate a Piltover Worker.

## Invariants Shared by Every Option

- A credential identifies exactly one Worker and grants no tenant, capability, lease, repository, or Codex authority by itself.
- Every Worker mutation revalidates credential, Worker ACTIVE state, capability coverage, exact tenant grant, P2 ancestry, and current lease as applicable.
- Credentials are never stored in Git, RunEvent, AuditEntry metadata, handoff evidence, application logs, URLs, or Codex protocol frames.
- Enrollment and credential lifecycle are human control-plane actions; a Worker cannot self-grant tenant access.
- Authority loss is fail-closed. Revocation, Worker disable, grant revoke, lease expiry/reclaim, or cancellation makes future authoritative mutation fail.
- Network requests use a versioned, strict, size-bounded typed contract and safe ErrorEnvelope responses.

## Option A — Opaque Bearer Credential over HTTPS

An authenticated P2 actor with `agent.manage` at an already-approved exact Worker target issues a cryptographically random 256-bit credential. The Worker receives the plaintext once through an Owner-controlled local enrollment step. The server stores only a credential ID, Worker ID, SHA-256 verifier, status, created/last-used/expiry/revocation timestamps, and attributable audit facts.

- Enrollment: human-approved, one-time plaintext delivery.
- Validation: `Authorization: Bearer <credential-id>.<secret>` over HTTPS; constant-time verifier comparison.
- Rotation: issue a replacement, activate it, then revoke the old credential atomically or with an explicitly bounded overlap.
- Revocation: immediate server-side denial; old leases remain historical but lose mutation authority.
- Expiration: required; maximum 90 days.
- Recovery: revoke and enroll a replacement; plaintext is never recoverable.
- Replay: bearer replay is possible if the secret is stolen. TLS, redaction, bounded expiry, rotation, lease fencing, idempotency, and rate limits reduce impact but do not provide cryptographic per-request replay prevention.

Benefits: smallest implementation, no dependency, conventional HTTP behavior. Cost: possession equals authentication until revoke/expiry.

## Option B — Ed25519 Signed Requests

The Worker generates an Ed25519 key pair locally. A human-approved, short-lived, single-use enrollment challenge binds its public key to one Worker. The server stores only public-key material and credential lifecycle facts. Each request signs the protocol version, Worker ID, HTTP method, canonical path, body hash, timestamp, and nonce. The server enforces a short clock window and durable nonce uniqueness.

- Rotation: enroll a new public key under an authenticated, audited control-plane action; revoke the old key.
- Revocation: immediate denial by key ID.
- Expiration: required for the public-key credential record.
- Recovery: revoke and re-enroll; no server-held private material exists.
- Replay: duplicate signed requests fail when the nonce is already consumed.

Benefits: non-recoverable server storage and explicit replay resistance. Costs: additional enrollment protocol, nonce persistence/retention, clock-skew policy, canonical request signing, and protected local private-key storage.

## Option C — Mutual TLS

Issue a client certificate per Worker and authenticate at a terminating proxy or application boundary. Certificate identity maps to one Worker; revocation and rotation use certificate lifecycle operations.

Benefits: mature mutual authentication and strong mutual identity. Costs: certificate authority/proxy operations, deployment coupling, more infrastructure, and no current package or repository support.

## Approved Machine Authentication

Use Option A for the initial one-Owner P4 POC, with all of these constraints:

1. 256-bit random credential generated by Node's built-in crypto API.
2. Server stores only a SHA-256 verifier and lifecycle/audit facts.
3. The presented credential separates a public lookup identifier from 256-bit secret material using a stable safe encoding, conceptually `<credential-id>.<secret>`.
4. Credential is bound to exactly one Worker and has a maximum lifetime of 90 days.
5. Rotation uses a maximum 10-minute overlap and both credentials authenticate only the same Worker; the old credential then fails.
6. Revocation is immediate and expiration is evaluated using the server/control-plane clock.
7. Recovery is revoke-and-re-enroll; secrets are never recoverable.
8. Worker-side plaintext is supplied through a process environment variable or an Owner-only local configuration file outside Git. The implementation must verify restrictive local access before use and must not print the value.
9. Bearer replay risk is accepted only for the bounded POC behind HTTPS, strict rate/body limits, P3 idempotency, current-lease fencing, and default-disabled feature governance. Option B remains the defined upgrade when stronger replay resistance is required.

This is the cheapest reversible route for one Owner and one primary Worker. A future move from bearer verifier to public-key credentials is additive: enroll the new credential kind, migrate Workers, then revoke bearer credentials without changing tenant grants or leases.

## Approved Transport

Use authenticated Worker-initiated HTTPS request/response polling on versioned routes. Do not add WebSocket, SSE, or an RPC framework in P4 R1.

- Worker opens only outbound HTTPS connections.
- Short polling handles claim and cancellation observation; heartbeat and lease renewal are explicit requests.
- P3 reconnect remains the canonical recovery contract after disconnect or restart.
- Every request is independently authenticated; connection lifetime is not authority.
- Routes remain disabled by the canonical feature-governance primitive until the dependency-security gate passes.
- No route accepts an arbitrary command, executable, environment map, filesystem path, Run lookup, or Codex JSON-RPC method.

This route minimizes dependencies and Next.js integration complexity. WebSocket can be proposed later if measured polling latency or load proves insufficient.

## Approved Worker Credential Persistence Contract

After the security gate is cleared, add one additive `WorkerCredential` model and migration with only fields that have an implementation consumer:

- `id`
- `workerId`
- `secretVerifier`
- `issuedAt`, `expiresAt`, `createdAt`
- `createdByUserIdentityId` when issuance is a human governance action
- `revokedAt`, `revokedByUserIdentityId` optional
- `supersededByCredentialId` and `rotationStartedAt` only if required by the implemented overlap algorithm

The Worker relation is restrictive. Credential lifecycle events are appended to existing AuditEntry evidence without secret material. No tenant scope or capability is stored on the credential.

## Security and Failure Cases

- Missing, malformed, wrong-Worker, expired, or revoked credential: deny before any authoritative Worker mutation.
- Authenticated Worker without exact grant, capability, or current lease: deny.
- Credential revoked while offline or during execution: reconnect and future event/result/renewal fail; local interruption is best-effort; Job remains durable.
- Historical lease or unrelated Run: execution envelope denied.
- Absolute path, traversal, mixed separator escape, unregistered alias, or junction/symlink escape: local resolution denied.
- App Server crash: never mark Run completed; preserve deterministic failure evidence and P3 retry authority.
- Duplicate transport delivery: P3 idempotency and lease fencing decide canonical effects.
